# BooM Gateway — Model Definition and Usage Guide

## How models flow through the stack

When you use `backend: "boom"`, a request passes through four layers. Each
layer has its own "model" field that must agree with the others.

```
                        model: "served-model"
                              │
┌──────────────────────────── ▼ ───────────────────────────────┐
│  1. Client config (configs/boom.yaml)                        │
│     boom.model = "served-model"                              │
│     → sent in the JSON body: {"model": "served-model", ...}  │
│     → sent with: Authorization: Bearer <boom.api_key>        │
└──────────────────────────── │ ───────────────────────────────┘
                              ▼
┌──────────────────────────── │ ───────────────────────────────┐
│  2. BooM Gateway (75-boom.yaml ConfigMap)                    │
│     model_list:                                              │
│       - model_name: served-model         ← matches request   │
│         litellm_params:                                      │
│           model: openai/served-model     ← provider prefix   │
│           api_base: http://router-service:8080/v1            │
│     → looks up model_name in model_list                      │
│     → forwards to api_base with the provider's model ID      │
└──────────────────────────── │ ───────────────────────────────┘
                              ▼
┌──────────────────────────── │ ───────────────────────────────┐
│  3. Router shim (/v1/chat/completions on port 8080)          │
│     → receives the request, enqueues it                      │
│     → model field is informational here                      │
└──────────────────────────── │ ───────────────────────────────┘
                              ▼
┌──────────────────────────── │ ───────────────────────────────┐
│  4. vLLM pods (--served-model-name served-model)             │
│     → the actual LLM serving the model                       │
│     → must have --served-model-name matching the chain       │
└─────────────────────────────────────────────────────────────┘
```

The golden rule: **`boom.model` in your client config must match a
`model_name` entry in BooM Gateway's `model_list`, and that entry must
route to a backend where vLLM serves under the same model name.**

---

## Layer 1: Client config (`configs/boom.yaml`)

This is what the load-test framework reads. The `boom.model` value gets
placed into every HTTP request body as `"model"`.

```yaml
backend: "boom"

boom:
  base_url: "http://<node-ip>:30401"
  chat_path: "/v1/chat/completions"
  model: "served-model"            # ← model name sent in every request
  api_key: "sk-boom-master"
  timeout_s: 1000.0
  stream: false
```

### Fields

| Field       | Description                                               | Default                     |
|-------------|-----------------------------------------------------------|-----------------------------|
| `base_url`  | BooM Gateway address (NodePort)                           | `http://127.0.0.1:30401`   |
| `chat_path` | API endpoint path                                         | `/v1/chat/completions`      |
| `model`     | Model name to request — must match BooM's `model_list`    | `served-model`              |
| `api_key`   | Bearer token — master key or a generated virtual key      | `sk-boom-master`            |
| `timeout_s` | Request timeout in seconds                                | `1000.0`                    |
| `stream`    | Streaming mode (not supported yet)                        | `false`                     |

### Changing the model name

If your vLLM serves a model called `"qwen3-8b"` instead of `"served-model"`,
update this field:

```yaml
boom:
  model: "qwen3-8b"
```

Then you must also update layers 2 and 4 to match (see below).

---

## Layer 2: BooM Gateway config (Helm ConfigMap)

BooM Gateway receives the request and looks up the `"model"` field in its
`model_list`. This config is generated by the Helm template
`vllm-kv-stack/templates/75-boom.yaml` and mounted into the pod at
`/app/boom_config.yaml`.

### Current default (single model, single backend)

The Helm template generates this ConfigMap:

```yaml
model_list:
  - model_name: served-model          # what clients request
    litellm_params:
      model: openai/served-model      # provider/model-id format
      api_base: http://router-service:8080/v1
      api_key: dummy

general_settings:
  master_key: "sk-boom-master"
```

### `model_list` entry anatomy

```yaml
- model_name: <public-name>           # name clients use in {"model": "..."}
  litellm_params:
    model: <provider>/<model-id>      # provider prefix + actual model ID
    api_base: <upstream-url>          # where to forward (must end at /v1)
    api_key: <upstream-key>           # key for the upstream (or "dummy")
    rpm: 60                           # optional: per-deployment RPM cap
    timeout: 1200                     # optional: upstream timeout (seconds)
  model_info:                         # optional metadata
    id: <deployment-id>               # unique deployment identifier
    input_cost_per_token: 0.000003    # optional: cost tracking
    output_cost_per_token: 0.000015
    quota_count_ratio: 1              # optional: quota multiplier
  flow_control:                       # optional: concurrency/context caps
    model_queue_limit: 50             # max in-flight requests
    model_context_limit: 5000000      # max in-flight input characters
```

### Provider prefix conventions

The `model` field under `litellm_params` uses a `provider/model-id` format.
BooM Gateway uses this to determine how to format the upstream request.

| Provider    | Prefix        | Example                              |
|-------------|---------------|--------------------------------------|
| OpenAI      | `openai/`     | `openai/gpt-4-turbo`                |
| Anthropic   | `anthropic/`  | `anthropic/claude-sonnet-4-20250514` |
| Azure       | `azure/`      | `azure/my-gpt4-deployment`          |
| Gemini      | `gemini/`     | `gemini/gemini-2.0-flash`           |
| Bedrock     | `bedrock/`    | `bedrock/anthropic.claude-3-sonnet`  |
| vLLM/custom | `openai/`     | `openai/served-model`               |

**For your local vLLM setup, always use `openai/<model-name>`** because
vLLM exposes an OpenAI-compatible API.

## Layer 3: Helm `values.yaml` — BooM deployment knobs

```yaml
boom:
  enabled: false              # set true to deploy the BooM pod
  image: boom-gateway:latest  # container image
  masterKey: "sk-boom-master" # admin master key
  nodePort: 30401             # external access port
  databaseUrl: ""             # optional Postgres for spend persistence
  resources:
    requests:
      cpu: "250m"
      memory: "128Mi"
    limits:
      cpu: "2000m"
      memory: "512Mi"
```

The `masterKey` is injected into the ConfigMap's `general_settings.master_key`.
The `databaseUrl` is optionally injected into `general_settings.database_url`
and also set as the `DATABASE_URL` environment variable.

---

## Layer 4: vLLM `--served-model-name`

vLLM pods are started with `--served-model-name served-model` (hardcoded in
`40-vllm.yaml`). This is the model name vLLM registers in its
`/v1/models` endpoint.

When BooM Gateway forwards to `http://router-service:8080/v1`, the router
dispatches to vLLM, and vLLM must recognize the model name in the request.

If you change the served model name, update `40-vllm.yaml`:

```
--served-model-name <your-model-name> \
```

And update the KV events config on the same line:

```
--kv-events-config '{"enable_kv_cache_events": true, "publisher": "zmq", "endpoint": "tcp://*:5557", "topic": "kv@'"${POD_NAME}"'@<your-model-name>"}' \
```

## Practical examples

### Example 1: Single model (default setup)

You're serving Qwen3-8B as `served-model`. This is the out-of-the-box setup.

**Client config** (`configs/boom.yaml`):
```yaml
backend: "boom"
boom:
  model: "served-model"
  base_url: "http://7.216.57.215:30401"
  api_key: "sk-boom-master"
```

**BooM config** (auto-generated by Helm):
```yaml
model_list:
  - model_name: served-model
    litellm_params:
      model: openai/served-model
      api_base: http://router-service:8080/v1
      api_key: dummy
```

**vLLM**: `--served-model-name served-model`

Nothing to change — everything matches.

---

### Example 2: Custom model name

You're serving GLM-5-w4a8 and want to call it `"glm5"`.

**Step 1 — Client config** (`configs/boom_glm5.yaml`):
```yaml
backend: "boom"
boom:
  model: "glm5"
  base_url: "http://7.216.57.215:30401"
  api_key: "sk-boom-master"

helm:
  model_name: "glm5"
  nfs_path: "/saeid/models/GLM-5-w4a8-mtp-QuaRot"
  vllm_quantization: "w4a8"
  vllm_enable_expert_parallel: true
```

**Step 2 — Update the Helm template** (`75-boom.yaml` ConfigMap section):

Change the `model_list` in the ConfigMap data:
```yaml
data:
  boom_config.yaml: |
    model_list:
      - model_name: glm5
        litellm_params:
          model: openai/glm5
          api_base: http://router-service:8080/v1
          api_key: dummy
```

Or, to make it dynamic (recommended), template the model name from
`values.yaml`:
```yaml
data:
  boom_config.yaml: |
    model_list:
      - model_name: {{ .Values.helm.model_name | default "served-model" }}
        litellm_params:
          model: openai/{{ .Values.helm.model_name | default "served-model" }}
          api_base: http://router-service:8080/v1
          api_key: dummy
```

**Step 3 — vLLM** picks up the model name from the Helm chart
(`--served-model-name` is hardcoded to `served-model` in `40-vllm.yaml` —
update it to match if you use a custom name).

---

### Example 3: Multiple models behind BooM (multi-model routing)

BooM Gateway supports multiple `model_list` entries. If you have two vLLM
deployments behind separate routers, you can expose both through a single
BooM Gateway instance.

**BooM config** (edit the `75-boom.yaml` ConfigMap):
```yaml
model_list:
  - model_name: qwen3-8b
    litellm_params:
      model: openai/qwen3-8b
      api_base: http://router-service:8080/v1
      api_key: dummy

  - model_name: glm5
    litellm_params:
      model: openai/glm5
      api_base: http://glm5-router-service:8080/v1
      api_key: dummy
```

Clients choose which model by setting `"model": "qwen3-8b"` or
`"model": "glm5"` in their requests. BooM Gateway routes to the correct
upstream based on the match.

---

### Example 4: Load balancing across multiple deployments of the same model

If you register multiple entries with the **same `model_name`**, BooM
Gateway automatically round-robins across them.

```yaml
model_list:
  - model_name: served-model
    model_info:
      id: cluster-a
    litellm_params:
      model: openai/served-model
      api_base: http://router-service-a:8080/v1
      api_key: dummy

  - model_name: served-model
    model_info:
      id: cluster-b
    litellm_params:
      model: openai/served-model
      api_base: http://router-service-b:8080/v1
      api_key: dummy
```

Clients just request `"model": "served-model"` and BooM distributes
across the two clusters.

---

### Example 5: Model aliases

Use `router_settings.model_group_alias` to let clients request a model
by an alias name that maps to a real `model_name`.

```yaml
model_list:
  - model_name: qwen3-8b
    litellm_params:
      model: openai/qwen3-8b
      api_base: http://router-service:8080/v1
      api_key: dummy

router_settings:
  model_group_alias:
    "default": "qwen3-8b"              # "default" → routes to qwen3-8b
    "chat-model":
      model: "qwen3-8b"
      hidden: true                      # hidden from /v1/models listing
```

Clients can request `"model": "default"` or `"model": "chat-model"` and
both resolve to the `qwen3-8b` model group.

---

### Example 6: External cloud providers alongside local vLLM

BooM Gateway can route to external APIs and your local vLLM simultaneously.

```yaml
model_list:
  - model_name: served-model
    litellm_params:
      model: openai/served-model
      api_base: http://router-service:8080/v1
      api_key: dummy

  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: ${OPENAI_API_KEY}

  - model_name: claude-sonnet
    litellm_params:
      model: anthropic/claude-sonnet-4-20250514
      api_key: ${ANTHROPIC_API_KEY}
```

Clients choose the model per request. The load-test framework only sends
to the model configured in `boom.model`, but external users hitting the
same BooM Gateway endpoint can request any model in the list.

## Advanced BooM Gateway configuration

### Rate limiting and plans

BooM Gateway supports per-key rate limiting through plans. These are
defined in the gateway config (not Helm values — edit the ConfigMap or
provide a custom config).

```yaml
rate_limit:
  enabled: true
  default_rpm: 60

plan_settings:
  default_plan: "basic"
  plans:
    basic:
      concurrency_limit: 4
      rpm_limit: 60
      window_limits:
        - [100, 18000]           # 100 requests per 5 hours
    pro:
      concurrency_limit: 10
      rpm_limit: 120
    enterprise:
      concurrency_limit: 50
      rpm_limit: 600
```

### Router settings

```yaml
router_settings:
  routing_strategy: round_robin      # or key_affinity
  model_group_alias:
    "gpt-4": "gpt-4o"               # simple alias
    "GPT-4o":
      model: "gpt-4o"
      hidden: true                   # hide from /v1/models
```

### Flow control (per-deployment)

Limit concurrency or total context per deployment to prevent overloading
a single backend.

```yaml
- model_name: served-model
  flow_control:
    model_queue_limit: 50            # max in-flight requests
    model_context_limit: 5000000     # max in-flight input characters
  litellm_params:
    model: openai/served-model
    api_base: http://router-service:8080/v1
    api_key: dummy
```

## Where each model field is configured

| Layer | File | Field | Example value |
|-------|------|-------|---------------|
| Client request body | `configs/boom.yaml` | `boom.model` | `"served-model"` |
| BooM Gateway lookup | `75-boom.yaml` ConfigMap | `model_list[].model_name` | `"served-model"` |
| BooM upstream call | `75-boom.yaml` ConfigMap | `model_list[].litellm_params.model` | `"openai/served-model"` |
| BooM upstream URL | `75-boom.yaml` ConfigMap | `model_list[].litellm_params.api_base` | `"http://router-service:8080/v1"` |
| vLLM serving name | `40-vllm.yaml` | `--served-model-name` | `"served-model"` |
| Helm model_name | `values.yaml` / client YAML | `helm.model_name` | `"served-model"` |

### Consistency checklist

When adding or changing a model, verify all four match:

1. `boom.model` in client config = `model_list[].model_name` in BooM config
2. `model_list[].litellm_params.model` = `openai/<model-name>` matching vLLM
3. `model_list[].litellm_params.api_base` = correct router/backend URL
4. `--served-model-name` in vLLM = the model name the chain expects

## Making the Helm template model-aware (optional improvement)

Currently `75-boom.yaml` hardcodes `served-model` in its ConfigMap. To make
it dynamic from Helm values, you can template the model name. Here is the
recommended change to the ConfigMap data section:

**Before:**
```yaml
data:
  boom_config.yaml: |
    model_list:
      - model_name: served-model
        litellm_params:
          model: openai/served-model
          api_base: http://router-service:8080/v1
          api_key: dummy
```

**After (dynamic):**
```yaml
data:
  boom_config.yaml: |
    model_list:
      - model_name: {{ .Values.aibrix.modelName | default "served-model" }}
        litellm_params:
          model: openai/{{ .Values.aibrix.modelName | default "served-model" }}
          api_base: http://router-service:8080/v1
          api_key: dummy
```

This reuses the existing `aibrix.modelName` value (which defaults to
`"served-model"` and is already set by `sweep_methods.py` for each
experiment). No new values.yaml fields needed.

## Troubleshooting model issues

| Symptom | Cause | Fix |
|---------|-------|-----|
| `{"error": "model not found"}` from BooM | Client's `boom.model` doesn't match any `model_name` in `model_list` | Update `boom.model` or add the model to the ConfigMap |
| `404` from router after BooM forwards | Router doesn't have a `/v1/chat/completions` shim | Rebuild router image from latest source |
| `{"error": "model ... not found"}` from vLLM | vLLM's `--served-model-name` doesn't match | Align the `--served-model-name` flag with the model chain |
| Request goes to wrong backend | Multiple `model_list` entries — wrong one matched | Check `model_name` uniqueness or use `model_info.id` to distinguish |
| BooM returns `502 Bad Gateway` | `api_base` in ConfigMap is wrong or router isn't running | Verify `router-service:8080` is reachable from inside the cluster |
| Rate limited unexpectedly | Plan or RPM limit hit | Check `rate_limit` and `plan_settings` in BooM config; use master key to bypass |
